# 设计

> 状态：一期已完成；二期 2a（region 切分与依赖检测）已完成，2b（接管原版 tick）未开始。最后更新 2026-11-14。

## 要解决什么

原版 Minecraft 1.20.1 的服务端主线程，一个 tick（50ms）里要跑完：

```
MinecraftServer.tickServer
├── tickChildren
│   ├── ServerFunctionManager.tick
│   ├── 每个 ServerLevel.tick          ← 13 个阶段，逐个世界全量跑
│   │   ├── WorldBorder / 天气 / 睡眠 / 日照 / 时间
│   │   ├── LevelTicks ×2（方块 + 流体，红石在这里）
│   │   ├── Raids
│   │   ├── ServerChunkCache.tick      ← 区块加载 + 区块 tick + ChunkMap
│   │   ├── runBlockEvents
│   │   ├── EndDragonFight
│   │   ├── EntityTickList.forEach      ← 实体 AI / 寻路 / 物理
│   │   ├── tickBlockEntities          ← 漏斗 / 熔炉 / 箱子
│   │   └── PersistentEntitySectionManager
│   ├── ServerConnectionListener.tick
│   ├── PlayerList.tick
│   └── GameTestTicker
└── saveEverything（自动保存）
```

真正在后台的只有三处：网络 IO（Netty）、区块 NBT 读写（`Worker-Main-N`）、渲染 mesh 构建（客户端）。

**关键事实**：1.20.1 的「多线程光照」是误导 —— `ThreadedLevelLightEngine` 只排队，计算仍在 server 线程；地形生成同理。所以「跑图卡」和「实体多卡」压在同一根线程上。

## 不做什么

- **不兼容全部 Forge mod**。明确放弃。只兼容自己选定的少数 mod，适配成本靠配置控制。
- **不改客户端渲染管线**。客户端仍单线程，只做优化。
- **不改游戏玩法与数值**。
- **不做地形生成**。归 `GTSN-Terrain-Generation`，本内核只提供调度接口（五期）。

## 五期划分

### 一期 · 可观测性（已完成）

26 个注入点（`tickServer` 7 + `tickChildren` 6 + `ServerLevel.tick` 13 的等价边界），全部 HEAD/RETURN 插桩。

产出：`/gtsnperf` 命令、定期日志、CSV 明细。

**为什么先做这个**：后面所有「拆哪个」的判断都依赖「谁在吃这 50ms」。没有它，模块化拆哪儿都是照别人的场景猜。

### 二期 · 并行度=1 的多线程骨架（2a、2b 已完成）

**2a（已完成）**：region 切分、串行调度、跨 region 依赖检测。全部零 MC 依赖，17 个单测覆盖。

- `RegionId` / `RegionMap` / `GridRegionMap` —— 区块 → region 映射（`floorDiv` 处理负坐标）
- `SimpleRegion` —— `Region` 的最小实现，只持状态
- `SerialRegionScheduler` —— 按 `RegionId` 排序串行 tick，union-find 做合并，DFS 检测任意环
- `ThreadGuard` —— 线程断言（不用 `RenderSystem.isOnGameThread()`，它在这个版本恒返回 true）

**为什么串行也能验证并行逻辑**：合并规则、访问检测、region 归属都不依赖真并发；只有「两个 region 同时写同一份数据」的竞态需要真并行才能暴露，那属于三期。先在串行下把逻辑跑对，三期只需把 `tickAll` 的执行方式换掉。

**2b（未开始）**：用 `@Redirect` 接管 `tickChildren` 里对 `ServerLevel.tick` 的调用，把 tick 交给调度器。这一步会改变原版调用路径，需要一致性测试兜底。

**一致性测试**（2b 的验收）：同种子 + 同操作序列，每 tick 世界状态哈希必须相同。过不了这关，说明转发层设计错了，后面全部免谈。

### 二期 2b · 接管原版 tick（已完成）

**做了什么**：`MinecraftServerMixin` 用 `@Redirect` 拦截 `tickChildren` 里对
`ServerLevel.tick(BooleanSupplier)` 的调用，转到 `bridge.TickRedirectHandler.dispatch`。

- 开关关闭（默认）：`dispatch` 直接调 `level.tick(hasTimeLeft)` —— 与原版**完全等价**，
  只是多一层静态调用。
- 开关开启（`-PregionEnabled` → `-Dgtsnkernel.region.enabled=true`）：走
  `SerialRegionScheduler`（并行度=1），每个维度一个 region。

**这是项目第一个改变原版调用路径的注入** —— 之前全是 HEAD/RETURN 打点，不改变行为。

**一致性验证**：`tools/consistency-check.sh` 用同一个基准世界跑两次，比对方块实体哈希。
两条路径的结果必须完全相同（实测 `881bd189827a5eac`，293 个方块实体）。

**踩到的两个坑**（都写进代码注释了）：

1. **Mixin 包保护**：`mixins.gtsnkernel.json` 把整个 `com.gtsn.kernel.mixin` 包声明为
   mixin 包，包里除 mixin 类之外的任何类都**不能被普通代码直接引用**，否则运行时抛
   `IllegalClassLoadError: ... is in a defined mixin package ... and cannot be referenced directly`。
   所以 `TickRedirectHandler` / `WorldHasher` 放在新包 `com.gtsn.kernel.bridge`。
2. **哈希不能用对象身份**：`BlockEntityType.hashCode()` 没重写，走 `Object.hashCode()`
   （内存地址），每次 JVM 启动都不同 —— 同一世界两次运行算出的 hash 必然不同，测试永远失败。
   必须用 `BuiltInRegistries.BLOCK_ENTITY_TYPE.getKey(type)` 的注册名。

### 三期的真实障碍（2026-11-14 实测）

**试过了**：把 `Level.tickBlockEntities()` 的 tick 循环按 region 分组，各组丢到
`RegionThreadPool` 的 lane 上并行，主线程 `allOf().join()` 等齐。

**结果**：服务端启动后第一 tick 就卡死，RCON 完全无响应，只能强杀。

**根因**（不是实现 bug，是原版线程模型的硬约束）：

```
主线程                          GTSN-Region-0
  allOf(futures).join()  ←──等待──  ticker.tick()
                                     └─ level.getChunk(...)
                                        └─ ServerChunkCache.getChunk()
                                           非主线程 → supplyAsync(..., mainThreadProcessor).join()
                                           ↑ 等主线程处理，但主线程在等它
```

`ServerChunkCache.getChunk` 在非主线程会**阻塞并把活转交主线程**（javadoc 自己写了
「在区块加载中调用会死锁」）。整个 `ServerChunkCache` 假定只有一个线程在 tick。

**所以三期不是「把循环并行」，而是「让每个 region 拥有自己的区块存储与调度队列」** ——
Folia 的做法（其 README 原话：region 之间并行但不并发，它们不共享数据）。这是重写
`ServerChunkCache` / `ChunkMap` / `ServerLevel` 的核心，量级是数月，且要逐个处理
mod 的跨区块假设。

**留下的东西**：
- `RegionThreadPool`（region → 固定 lane 的绑定，四期还能用）
- `ParallelBlockEntityTick`（分组逻辑本身没问题，缺的是线程模型支持）
- `-PparallelBlocks` 开关与一致性测试的第三场景（默认不开）

### 三期前置 · profiler 按线程分桶（已完成）

三期换成线程池后，同一个阶段会在多个线程上同时跑。原来的「只采集 owner 线程 + 全局数组」
那时候会是数据竞争，也回答不了「哪个 region 慢」。

现在每个线程一个桶（容量 16，超出计数不静默丢）。`/gtsnperf` 显示 `采集桶 N 线程`；
`StageProfiler.perBucketStats()` 给每个线程的明细。

开销 73.9 ns/对（分桶前 65.5 ns），每 tick 0.0022 ms。

**顺带修掉一个一直在错的 bug**：环形缓冲读取从 `head` 开始（那是「下一个写入位」），
只有写满时才恰好正确 —— 短窗口采样的 p50/avg 全被 0 值污染。

### 三期 · region 切分 + 真并行

按玩家位置与区块邻接切 region，每 region 一线程。实体 / 方块实体 / 随机 tick / 刷怪按 region 并行。

**优先级按实测数据排**（见 `docs/实测数据.md`）：

| 目标 | 占主线程 | 跨 region 依赖 | 顺序 |
| --- | --- | --- | --- |
| 方块实体 | 32.3% | 中等（漏斗只跟相邻方块交互） | **先做** |
| 实体 | 54.3% | 严重（AI 目标 / 伤害 / 传送都跨区块） | 后做 |
| 区块系统 | 12.5% | 低 | 最后 |

原计划把「区块生成并行」排在三期，实测显示稳态下区块只占 12.5%（其中区块管理 3.6%），
收益远低于预期 —— 优先级往后放。

**验收**：跑图场景 TPS ≥ 1.3×，否则停下重新评估。

### 四期 · 兼容层

- `compat-probe` 模式：单线程跑一遍，记录每个 mod 的访问模式
- 规则表：`affinity_radius` / `exclusive_thread` / `static_unsafe`
- region 依赖图 + 自动合并
- 运行时降级

**目标**：适配一个新 mod = 加一条 JSON，不改 mod 代码。

### 五期 · 地形生成接口

`GenerationScheduler`：内核决定在哪个线程生成、地形 mod 负责生成什么。

三条约束：生成阶段不碰 `Level`、注入必须在目标 region 线程、同一 `ChunkPos` 串行。

## 核心设计：跨 region 访问协议

这是整个方案与 Folia 最大的分歧点。

| | Folia | 本方案 |
| --- | --- | --- |
| 跨 region 访问 | **抛异常**，插件必须改写 | 读放行 / 写排队 / 同步调用**自动合并 region** |
| 生态要求 | 插件写 `folia-supported: true` | mod 原样加载，配置适配 |
| 并行度 | 固定 | 随兼容需求自动退化 |
| 失败模式 | 崩 | 降级 + 告警 |

**取舍：用并行度换兼容性，且这个交换由运行时自动完成。**

死锁避免靠 region 依赖图：检测到 A→B 与 B→A 同时存在 → 合并两者 → 永不重入。

## 否决的方案

| 方案 | 否决理由 |
| --- | --- |
| Mixin `@Overwrite` 改 `ServerLevel.tick` | 与所有优化 mod 冲突；`ServerLevel.tick` 的 13 个阶段是内联循环，Mixin 做不到结构化拆分 |
| 照搬 Folia 硬失败 | 违背「适配成本低」的目标 |
| 只做算法优化（Lithium 路线） | 拿不到真并行，天花板低 |
| 客户端也 fork | Forge 客户端 mod 大量 mixin 渲染类，fork 后全断，无先例 |
| 全 region 无锁 + 乐观并发 | 冲突检测开销在 MC 的对象图上不可控 |
| 兼容全部 Forge mod | 与多线程 tick 本质冲突，TickThreading 死过一次 |

## JDK 25

**结论：现有栈跑不了，要上得换栈。**

实测与本机调研（2026-11-14）：

| 障碍 | 事实 |
| --- | --- |
| Gradle | 8.14 读不了 class 69（实测 `Unsupported class file major version 69`）。JDK 25 需要 Gradle 9.1+ |
| ASM | Forge 47.4.0 自带 9.7.1，只认到 class 68。Mixin 不重打包 ASM，换 classpath 上的 jar 即可升到 9.10.1 |
| SecurityManager | `-Djava.security.manager=allow` 在 JDK 25 上 VM 直接退出（JEP 486） |
| ModLauncher | 10.0.9 只用 ASM 9.x 老 API，向后兼容，不用升 |

**可行路径**（未验证）：
- 构建：JDK 21 + Gradle 8.14（已验证可用）
- 目标字节码：17
- 运行：JDK 25 + ASM 9.10.1 + `--add-opens` 一组

收益（值得做的理由）：JDK 25 的**紧凑对象头**（JEP 519）让对象头 12→8 字节，MC 堆里全是小对象，能省 15-25% 堆内存并改善缓存局部性 —— 对 region 并行后缓存压力更大的场景尤其有用。

**当前状态**：`build.gradle` 里有 `-Pjdk25` 开关（切 toolchain + 强制 ASM 9.10.1），但**未实测通过**。
