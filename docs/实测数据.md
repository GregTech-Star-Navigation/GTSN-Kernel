# 实测数据

> 最后更新 2026-11-14。数据来自本机（Windows 11 / Ryzen 类桌面 CPU）自建压测，非玩家真实整合包。

## 怎么测的

服务端 `gradlew runServer` 会吞掉 stdin，所以 `/gtsnperf` 没法通过管道送进去。用 **RCON** 从外部驱动：

```properties
# run/server/server.properties
enable-rcon=true
rcon.port=25575
rcon.password=gtsnkernel
```

```bash
node tools/rcon.mjs "fill -16 -60 -16 16 -60 16 minecraft:hopper"   # 1088 个方块实体
node tools/rcon.mjs "summon minecraft:zombie 0 -60 0"                # 循环 200 次
node tools/rcon.mjs "gtsnperf"
```

`tools/rcon.mjs` 是最小 RCON 客户端（Node 内置模块，无依赖），`--wait N` 会轮询直到服务端就绪。

**超平坦世界的注意点**：1.20.1 的 superflat 地面在 **y = -61**，不是 y = 4。第一次用 y=4 铺漏斗得到 `No blocks were filled`。

## 结果

### 空载 vs 有负载

| 阶段 | 空载 | 有负载（1088 漏斗 + 1089 熔炉 + 200 僵尸） | 倍数 |
| --- | --- | --- | --- |
| 服务器总 | 0.67 ms | **6.83 ms** | 10.2× |
| 世界 tick | 0.21 ms | 6.78 ms | 32× |
| 实体 | ~0 ms | **3.71 ms** | — |
| 方块实体 | ~0 ms | **2.20 ms** | — |
| 区块系统 | 0.20 ms | 0.86 ms | 4.3× |
| 区块管理 | 0.08 ms | 0.25 ms | 3.1× |

### 有负载时的占比（600 tick 样本）

| 阶段 | avg | p95 | max | 占服务器 tick |
| --- | --- | --- | --- | --- |
| **实体** | 3.709 | 6.040 | 10.272 | **54.3%** |
| **方块实体** | 2.204 | 2.464 | 4.791 | **32.3%** |
| 区块系统 | 0.855 | 1.062 | 1.441 | 12.5% |
| ├ 区块管理 | 0.245 | 0.285 | 0.532 | 3.6% |
| 方块/流体 tick | ~0 | ~0 | 0.001 | ~0% |
| 袭击 / 玩家 / 网络 | ~0 | ~0 | 0.07 | ~0% |

`level_tick` = 6.783 ms，占 `server_tick` 的 99.4%；`entities + block_entities + chunk_cache` = 6.768 ms，与它基本吻合（差额是未单独计时的 weather / time / dragon 等）。

## 结论：三期该并行什么

**实体（54%）+ 方块实体（32%）= 86.6% 的主线程时间。**

区块系统只有 12.5%，其中真正的区块管理（加载/卸载/实体追踪）3.6%。

**这推翻了「区块生成是最大瓶颈」的先验假设** —— 至少在「区块已加载完、实体密集」的场景下不成立。C2ME 的 34× 是**生成期**的收益，不是稳态 tick 的收益。

对三期的直接影响：

| 目标 | 占比 | 跨 region 依赖 | 结论 |
| --- | --- | --- | --- |
| 实体 tick | 54.3% | **严重**（AI 目标、伤害、传送都跨区块） | 收益最大，但最难 |
| 方块实体 | 32.3% | 中等（漏斗只跟相邻方块交互） | **性价比最高** |
| 区块系统 | 12.5% | 低 | 收益有限 |

所以三期应该**先做方块实体按 region 并行**（收益 32%，依赖面小），再做实体。原计划里「区块生成并行」在稳态 tick 下收益只有 3.6%，优先级应该往后放。

## 修掉的 bug

第一次压测时 CSV 的 `level_tick` 是 **0.005 ms**，而 `/gtsnperf` 显示 1.377 ms —— 差了 275 倍。

**原因**：`LEVEL_TICK` 在一个 tick 内会被多个维度（主世界 / 下界 / 末地）各调一次，环形缓冲记录的是「单次样本」，CSV 取最后一个样本，只拿到了最后一个维度（通常几乎空）。

**修复**：`StageProfiler` 加 `TICK_TOTALS` 累加器，`end()` 时累加，`tickTotalMs()` 读本 tick 总量，`endTick()` 在 tick 末尾清零。CSV 改用 `tickTotalMs`。

修复后 `level_tick` = 6.783 ms，与 `server_tick` 6.826 一致。

**这个 bug 只在多维度下出现** —— 单维度世界（或只测主世界）测不出来。

## 第二轮：区块生成期 + GTCEu

### 区块生成/加载

删世界、改 `level-type=minecraft:normal`、用 `/forceload` 分批加载：

| 已加载区块 | server_tick | chunk_cache | chunk_map |
| --- | --- | --- | --- |
| ~2048 | 0.956 | 0.247 | 0.089 |
| ~4096 | 1.115 | 0.252 | 0.090 |
| ~6144 | 1.385 | 0.330 | 0.139（max 14.779） |

**即使加载到 6144 个区块，`server_tick` 也只有 1.385ms** —— 对比实体负载的 6.83ms，区块生成/加载确实不是稳态大头。

启动期有一个 **408ms 的尖峰**（`server_tick` max），但那是 spawn chunk 一次性预生成，不是持续负载。

### GTCEu（可选依赖）

`./gradlew runServer -PwithGtceu` 会引入 GTCEu 7.5.4-patch01 + LDLib + Registrate + Configuration。默认不引入，避免每次构建都拉组织私有包。

**反直觉的结果**：

| 负载 | 数量 | 方块实体耗时 |
| --- | --- | --- |
| 原版漏斗 + 熔炉 | 2177 | **2.204 ms** |
| GT 机器（lv_macerator + lv_assembler） | 799 | **0.143 ms** |

**GT 机器比原版漏斗轻 15 倍** —— 因为它没有能量就跳过 tick。

所以「GT 整合包卡」不能简单归因于「机器多」。真实成本取决于：
- 机器是否有能量（没能量几乎零成本）
- 是否在跑配方（配方查找、进度推进）
- 是否有 multiblock（结构检查）
- 是否有覆盖板 / 电缆 / 管道网络

**这个测试不代表真实 GT 场景** —— 要测得有玩家、有电缆、有发电机，让机器真的在跑。

### 对三期的修正

原结论「实体 54% + 方块实体 32%」里的「方块实体 32%」是**原版漏斗**的数据。GT 机器空转只有 0.143ms，占比不到 1%。

所以三期优先级需要**按机器类型细分**，而不是笼统地「方块实体」。至少要区分：
- 原版方块实体（漏斗/熔炉/箱子）—— 重
- GT MTE 空转 —— 轻
- GT MTE 工作中 —— **未知，需要真实场景测**

## 第三轮：profiler 自身开销 + GT 机器放置限制

### profiler 开销（微基准）

`StageProfilerOverheadTest`（100 万次 begin+end，预热 20 万次）：

| 状态 | 每次 begin+end | 每 tick（30 对） | 占 5ms tick |
| --- | --- | --- | --- |
| 关闭 | 9.1 ns | ~0 | ~0% |
| 开启 | **65.5 ns** | **0.0020 ms** | **0.04%** |

**优化前是 2.2%**：`begin/end` 每次都调 `ThreadLocal.get()`，52 次/卡顿 × 约 2μs。
改成静态数组 + owner 线程比较后降到 0.04%，快了 50 倍。

代价：不再支持多线程采集（本来也只采集 owner 线程，多 region 之后要按 region 分桶，
那时候再引入 per-region 数组）。

**结论：profiler 可以常开。** 之前 `/forge tps` 测出的 on/off 差异（4.343 vs 4.440）
在负载波动范围内，说明开销已经低于测量噪声。

### GT 机器放置限制（踩坑）

用命令摆 GT 机器时发现：

1. **批量 `fill` 几乎全失败**，只能逐个 `setblock`。`fill ... gtceu:lv_macerator` 返回
   `Successfully filled 1 block(s)` 或 `No blocks were filled`。
2. **机器需要下方有支撑**：`setblock 0 100 0 gtceu:lv_macerator` 在悬空处失败
   （`Could not set the block`），下方铺一层 stone 后成功。
3. 不同机器名要试：`gtceu:lv_macerator` ✅、`gtceu:lv_assembler` ✅、
   `gtceu:hp_steam_macerator` ✅、`gtceu:lv_furnace` ❌（不存在）、
   `gtceu:lv_solar_panel` ❌、`gtceu:lv_energy_converter` ❌。
4. `gtceu:creative_energy` ✅ 存在，可以给机器无限供电 —— 但没法批量摆。

**所以「用命令摆一个真实的 GT 工厂」不可行**，需要真实存档。这一轮的 GT 数据只有空转值。

### 停服方式（环境教训）

一直用 `Stop-Process` 强杀服务端会导致 **Gradle transform 缓存损坏**
（`Could not read workspace metadata from .../transforms/*/metadata.bin`），
下一次构建直接失败，必须删 `~/.gradle/caches/8.14/transforms` 重建。

**正确做法**：`node tools/rcon.mjs "stop"` 优雅停服，等进程退出（exit code 0）。
